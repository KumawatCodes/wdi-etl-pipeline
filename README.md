# WDI Warehouse and Apache Superset on AWS

This repository provisions one Ubuntu EC2 host in `ap-south-1` with Terraform and runs PostgreSQL and Apache Superset using Docker Compose. Superset is for manual browser-based work: **you create the database connection, datasets, charts, filters, and dashboards in the Superset UI.** No dashboard objects are generated by these scripts.

For a complete project handoff covering the ETL, warehouse schema, local and AWS architecture, operating procedures, safety rules, and known issues, see [Project Context](docs/PROJECT_CONTEXT.md).

## Target layout

```text
Browser at http://127.0.0.1:8088
        │ SSH tunnel (port 8088)
        ▼
Ubuntu 24.04 LTS EC2 (m7i-flex.large, Mumbai)
  ├── Apache Superset 6.0.0
  └── PostgreSQL 17.6
       ├── wdi_db             existing WDI warehouse
       └── superset_metadata  Superset users and saved UI objects
        │
        └── Docker volume on encrypted 80 GiB gp3 EBS root disk
```

The security group permits SSH from `my_ip_cidr` only. The Superset and PostgreSQL ports bind to EC2 loopback; PostgreSQL has no public ingress rule. Use the SSH tunnel for the browser. Docker volumes and the encrypted EBS root disk remain when EC2 is stopped and started again. The Terraform EC2 resource has deletion protection and `prevent_destroy` enabled.

## Important data migration gate

The local Docker daemon was unavailable during this project review, so the contents of the existing `wdi_pgdata` volume could not be checked or backed up here. The deploy script therefore requires verified custom-format dumps of **both** `wdi_db` and `superset_metadata`. It restores only into empty databases and refuses to overwrite objects. It never runs `docker compose down -v`, `terraform destroy`, or a destructive database restore.

Keep a second copy of the verified archives outside this repository and outside the EC2 host. Backups under `backups/` are ignored by Git, but that does not protect them from disk loss.

## 1. Set application secrets

Create the dedicated Compose environment file. Do not copy the repository's existing `.env`; it contains AWS credential settings and is not transferred to EC2.

```bash
cp .env.example .env.compose
chmod 600 .env.compose
```

Replace every `REPLACE_WITH_...` value with a unique, long random value. For example, run `openssl rand -hex 32` separately for the database password, Superset secret key, read-only warehouse password, and Superset admin password. Keep `.env.compose` private and never commit it.

For local use of an already initialized PostgreSQL volume, `DB_PASSWORD` must match the role password already stored in that database. Changing the container environment does not rotate a password inside an existing PostgreSQL volume. For the new EC2 database, the value initializes the new PostgreSQL instance.

## 2. Prepare Terraform inputs

Generate a dedicated SSH key pair. Its private half is ignored by Git and stays on your machine:

```bash
scripts/prepare_ssh_key.sh
```

Update the existing `terraform/terraform.tfvars` with your current public IPv4 CIDR, preferably a single IP ending in `/32`. The old `db_password` entry is retained only for compatibility and is not used by this EC2 stack. The SSH public key defaults to `keys/wdi-superset-admin.pub`.

Terraform uses the default VPC in Mumbai and the latest Canonical Ubuntu 24.04 LTS x86_64 AMI. It creates an EC2 key pair, a security group, and an encrypted gp3 root volume. No RDS, load balancer, Kubernetes, Elastic IP, or other application infrastructure is created.

## 3. Validate and review cost before provisioning

Run the local checks first:

```bash
terraform fmt -recursive
terraform -chdir=terraform init
terraform -chdir=terraform validate
docker compose --env-file .env.example config --quiet
for script in scripts/*.sh; do bash -n "$script"; done
```

Then create and inspect a plan. A plan reads AWS metadata but does not create resources:

```bash
terraform -chdir=terraform plan -out=tfplan
terraform -chdir=terraform show tfplan
```

The expected resources are one EC2 instance, one security group, and one EC2 key pair; the root disk is part of the EC2 instance. Confirm that the plan uses `ap-south-1`, `m7i-flex.large`, Ubuntu 24.04, an 80 GiB encrypted gp3 disk, and your `/32` SSH CIDR. If your account lacks instance quota or access, stop here and review the account plan before changing the instance type.

**Do not apply until the reviewed plan and charge estimate are approved.** The m7i-flex.large type appears in AWS's current eligible EC2 types for qualifying new accounts, but free usage depends on account age, plan, remaining credits, and usage limits. Check the Billing console for your student account's actual credits and forecast. [AWS Free Tier eligibility](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-free-tier-usage.html)

Using AWS's current Mumbai price list, the estimate is **$0.10075 per EC2 running hour**, **$0.005 per in-use public IPv4 hour**, and **$0.0912 per GiB-month for gp3**. At 730 running hours/month, that is about **$73.55 EC2 + $3.65 IPv4 + $7.30 for 80 GiB EBS = $84.50/month**, before data transfer, snapshots, taxes, or credits. If used for 8 hours in a month and stopped the rest of the time, the same estimate is about **$0.85 compute/IP + $7.30 EBS = $8.15/month**. Stopping EC2 releases its automatically assigned public IP, but EBS storage remains billable. These are list-price estimates; confirm your account's current rates and credits in the [AWS Pricing Calculator](https://calculator.aws/#/) and Billing console before approval. [AWS regional price list](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonEC2/current/ap-south-1/index.json), [Public IPv4 pricing](https://aws.amazon.com/vpc/pricing/), [EC2 stop behavior](https://docs.aws.amazon.com/cli/latest/reference/ec2/stop-instances.html)

## 4. Back up the existing databases

Start the current local Postgres container if needed, then create and verify both archives:

```bash
scripts/backup_db.sh
```

The script uses `pg_dump` custom format, checks each archive with `pg_restore --list`, and prints SHA-256 checksums. Review the row counts and archive sizes, then copy both files to a separate safe location. The later deployment command requires their paths.

If Docker is unavailable, the database is not running, or the backup check fails, stop and resolve that before provisioning. The raw CSV file is not a substitute for a verified database backup.

## 5. Provision only after approval

After the plan and costs are approved, the operator can run:

```bash
terraform -chdir=terraform apply tfplan
```

This creates billable AWS resources. This repository's implementation session does not run `apply`.

## 6. Transfer and restore the existing warehouse

Put the verified dumps under the ignored `backups/` directory. Run the following with the actual filenames from the backup step:

```bash
WDI_WAREHOUSE_BACKUP=backups/wdi_db-<timestamp>.dump \
SUPERSET_METADATA_BACKUP=backups/superset_metadata-<timestamp>.dump \
scripts/deploy.sh
```

The script transfers only the Compose app configuration and the two specified database archives. It does not transfer `.env`, AWS credentials, Terraform state, or the raw CSV. It initializes the two databases on the new EBS-backed Postgres volume, restores only into empty databases, creates a read-only `superset_reader` account for WDI queries, upgrades Superset metadata, and creates the configured administrator only if that username is absent. Existing Superset users and saved objects in the metadata backup keep their current credentials.

If you are intentionally creating a new empty warehouse instead of migrating one, do not use `deploy.sh` as written: it deliberately requires both archives. The non-destructive schema helper is `scripts/init_warehouse_schema.sh`; it creates missing WDI tables and does not drop existing objects.

## 7. Open Superset and build dashboards manually

Start EC2 and get the current SSH tunnel command:

```bash
scripts/ec2_start.sh
scripts/instance_info.sh
```

Run the printed tunnel command in a terminal, then browse to **http://127.0.0.1:8088**. For a new metadata database, sign in with the username and password in `.env.compose`. If metadata was restored and already contains an administrator, use that existing account. `scripts/verify_remote.sh` checks Superset's health endpoint and tests the `superset_reader` PostgreSQL login after deployment.

In Superset, add a PostgreSQL connection manually. Use host `postgres`, port `5432`, database `wdi_db`, username `superset_reader`, and the `SUPERSET_READER_PASSWORD` value from `.env.compose`. The SQLAlchemy URI form is:

```text
postgresql+psycopg2://superset_reader:<URL-encoded-password>@postgres:5432/wdi_db
```

Then create your datasets, charts, filters, and dashboards in the Superset UI. No automation in this repository creates these objects.

## Day-to-day commands

```bash
scripts/status.sh                 # EC2, systemd, and container health
scripts/logs.sh superset          # follow Superset logs
scripts/logs.sh postgres          # follow PostgreSQL logs
scripts/ec2_stop.sh               # stop compute without deleting EBS data
scripts/ec2_start.sh              # start compute; public IP may change
scripts/instance_info.sh          # current public IP, SSH, and tunnel commands
scripts/backup_db.sh              # verified dumps of both databases
```

After EC2 starts, Docker and the systemd `wdi-compose.service` bring the containers back. Compose restart policies also restart containers after a Docker daemon restart. To restore a database, use `scripts/restore_db.sh` only for an empty target; it refuses to overwrite existing objects.

Do not run `docker compose down -v`, `terraform destroy`, or delete the EC2 root volume if you need to preserve the warehouse and dashboards. Stopping EC2 pauses compute charges, but EBS and retained backup storage continue to incur charges. The RDS service is not used.
